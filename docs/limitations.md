# 限制与已知问题

## 硬件/平台

- **只在一种配置上验证过**：双 RTX 3080-20G（魔改 GA102）/ X99 / PCIe
  3.0 x16 / 内核 6.x / 驱动 595.91.07。其他 GPU 代际、平台、驱动版本
  理论可行（社区 tinygrad/Aikitoria 补丁覆盖 3090/4090/5090），但本仓库
  的补丁未在这些组合上回归；
- BAR1 窗口大小是驱动侧稀缺资源，信箱落窗与启动期显存分配顺序强耦合
  ——这是整个方案最脆弱的一环（有垫片预推 + 16 轮重试 + 双侧一致性
  集合通信护栏，但本质是在和驱动分配器博弈）；
- 需要 root 常驻魔改驱动，与桌面/日常用途冲突（切回官方驱动需重新
  卸载/加载模块并 FLR）。

## 协议/软件

- **world_size == 2 only**：pairwise 锁步协议，TP>2 需要环形/树形扩展
  （未实现）；
- 单次 AR ≤ 24MB：半区容量硬上限，超限静默回落 NCCL（`should_custom_ar`
  门控）；
- TP=2 双进程架构下所有通信走跨进程 IPC 句柄交换（all_gather_object
  锁步纪律：失败一侧必须跳过 gather 保持两侧代际一致，代码有注释）；
- 驱动魔改未做任何形式的安全审计；P2P 写绕过了 WDDM/驱动层的隔离
  检查，属于"实验室可信双卡"场景。
- D-state 卡死风险：P2P/FLR 调试中内核态死锁表现为用户进程不可中断
  睡眠，只能整机重启（看门狗是缓解不是修复）。

## 收益边界（先算账再上）

- 端到端收益 = AR 占比 × 链路优势。decode 场景 AR 占 ITL 2~3%，
  别指望 decode 变快很多；prefill 场景 AR 占 ~21%（chunk 1024 口径），
  NCCL 已能用 P2P 的环境下链路优势只剩 4~5% → 端到端 ~+1%；
- 消费卡默认态（NCCL SHM 中转 6.9 GB/s）迁移到本方案是收益最大的场景；
- 计算×通信重叠（分段 AR）在 AWQ 量化模型 + 小 chunk 上净收益 ≈0
  （weight 重读损失吃掉重叠收益），除非你的模型是 dense bf16 且
  chunk 很大——见 performance.md 第 3 节的完整数据。
